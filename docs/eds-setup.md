# ЭЦП: NCALayer, eGov mobile, eGov Business — подключение и запуск

## Как устроено

Пользователь подписывает данные своим ключом, сервер проверяет подпись. Ключ никогда не попадает на сервер
(хранение ЭЦП-ключей на сервере — грубейшее нарушение ИБ). Различается только способ получить подпись;
проверка одна и та же (`app/modules/documents/eds.py` → NCANode):

| Способ | Где ключ | Как данные доходят до подписанта |
|---|---|---|
| NCALayer (компьютер) | файл `.p12`, Казтокен, ID-карта | страница отправляет данные в NCALayer по WebSocket `wss://127.0.0.1:13579`, тот спрашивает ключ и пароль и возвращает CMS |
| eGov mobile / eGov Business (телефон) | личная ЭЦП / ЭЦП компании в приложении | сайт показывает QR (`mobileSign:` + адрес «API №1»), приложение скачивает документ, подписывает и отправляет подпись обратно |

Сервер проверяет (`GOV-DS-02/03`): целостность (подписаны именно наши байты), цепочку до корневых
сертификатов НУЦ РК, срок действия на момент подписи, отзыв (OCSP), метку времени TSP, принадлежность БИН/ИИН.

Ключи: для **входа** — ключ AUTH (`extKeyUsage 1.3.6.1.5.5.7.3.2`), для **подписи документов** — ключ
подписи RSA/ГОСТ (`1.3.6.1.5.5.7.3.4`); NCALayer показывает пользователю только подходящие.

## Вход по ЭЦП: challenge-response

1. Сервер выдаёт одноразовый nonce (192 бита) с временем жизни 5 минут; в базе хранится только хеш.
2. Nonce привязан к браузеру, который его запросил (cookie `abdex_eds`): nonce, полученный в одном браузере
   и подписанный в другом, не принимается — это закрывает «подпиши, пожалуйста, вот этот текст».
3. Подпись проверяется над тем самым nonce; nonce погашается сразу после проверки, в том числе неудачной.
4. ИИН берётся только из проверенного сертификата (поле `serialNumber`), никогда из данных браузера.
5. Вход разрешён, если этот ИИН привязан к аккаунту («Безопасность» → «Вход по ЭЦП»). После входа действует
   обычная политика второго фактора. Лимиты попыток — общие для всех процессов (Redis).

Вход через eGov mobile устроен так же: QR одноразовый (5 минут), результат получает только браузер,
начавший вход.

## Подписание документов

Документ сделки формируется в PDF один раз и хранится в неизменном виде (SHA-256 фиксируется при создании);
перед подписью хеш сверяется — подписывается ровно тот файл, который хранится. Каждая сторона подписывает
своей ЭЦП (NCALayer или eGov mobile/Business), подписи хранятся вместе с результатом проверки и могут быть
перепроверены в любой момент (страница «Подписи»).

## Подключение

### 1. NCANode — проверка подписей (обязательно)

В боевом стеке (`deploy/docker-compose.prod.yml`) NCANode уже есть и доступен приложению по
`http://ncanode:14579`; наружу не публикуется. Ему нужен исходящий доступ к `ocsp.pki.gov.kz`,
`tsp.pki.gov.kz`, `crl.pki.gov.kz`. Закрепите проверенную версию образа (`malikzh/ncanode:<тег>`).

### 2. NCALayer (без договоров)

Пользователь ставит NCALayer с https://ncl.pki.gov.kz/. Если программа не запущена, сайт показывает
ссылку на установку. Если браузер (Chrome и другие) запрещает сайту обращаться к `127.0.0.1` — новое
разрешение «Доступ к локальной сети» (Local Network Access), — сайт подсказывает, где его включить.
Поддерживаются старые версии NCALayer (модуль `commonUtils`) и текущие (`basics`), любые хранилища ключей
(файл, KAZTOKEN, удостоверение личности, eToken, aKey). Протокол сверен с эталонным клиентом
`ncalayer-js-client` (SIGEX).

### 3. eGov mobile / eGov Business — два пути (оба реализованы, переключаются настройкой)

1. **Через SIGEX — `EGOV_PROVIDER=sigex`** (рекомендуется для запуска). Работает сразу, без регистрации в
   Smart Bridge: сервер регистрирует процедуру в SIGEX (`POST /api/egovQr`), показывает пользователю их
   QR-код и ссылки запуска, передаёт документ и ждёт подпись в фоне. Полученная подпись **проверяется у нас
   через NCANode** так же, как любая другая — SIGEX не нужно доверять на слово. Все запросы идут с
   бэкенда (как советует SIGEX); адреса, которые приходят от SIGEX, проверяются (только `SIGEX_URL`).
   Документ передаётся оператору — это отражено в реестре обработки ПДн (запись `egov_sign`) и должно
   быть в политике ПДн. Для коммерческой нагрузки оформите тариф SIGEX (Pro) и уточните их лимиты.
2. **Официально через Smart Bridge — `EGOV_PROVIDER=direct`** (smartbridge.egov.kz): нужна регистрация и
   заявка на сервис QR-подписания; рассмотрение может занять время. Сайт уже реализует протокол:
   одноразовые адреса «API №1» (`/egov/mgov/<токен>`) и «API №2» (документ и приём подписи), QR с префиксом
   `mobileSign:`. В заявке укажите эти адреса на вашем домене (`PUBLIC_BASE_URL`). Сначала пройдите
   тестовую среду (sandbox) Smart Bridge — тестирование сразу на продуктиве может привести к блокировке.
   После одобрения переключите `EGOV_PROVIDER=direct` — для пользователей ничего не меняется.

Ограничения eGov mobile: нужен личный телефон с интернетом, токены и смарт-карты не поддерживаются — поэтому
NCALayer остаётся вторым вариантом.

**Диплинки** (подписание на том же телефоне, где открыт сайт): под QR есть кнопки «Открыть в eGov mobile» /
«Открыть в eGov Business». В старой документации Smart Bridge адрес «API №1» оборачивался в
`mgovsign.page.link` — этот сервис ссылок (Firebase Dynamic Links) закрыт в 2025 году. Сайт использует
формат, который приложения принимают сейчас (сверено с ссылками, которые выдаёт SIGEX):

```
https://m.egov.kz/mobileSign/?link=<адрес API №1>?mgovSign      (eGov mobile)
https://m.egov.kz/businessSign/?link=<адрес API №1>?mgovSign    (eGov Business)
```

Если формат снова изменится, его можно задать без выпуска версии: `EGOV_DEEPLINK_MGOV`,
`EGOV_DEEPLINK_BUSINESS` (`{link}` — адрес API №1 с `?mgovSign`); пустое значение скрывает кнопку.
QR-код (`mobileSign:` + адрес API №1) работает независимо от диплинков.

Форматы обмена сверены с эталонной реализацией SIGEX (`sigex-qr-signing-client`): ответ API №1
(`description`, `expiry_date`, `organisation` с БИН, `document.uri`, `auth_type`), документы API №2
(`signMethod: CMS_SIGN_ONLY`, `documentsToSign[].document.file` с `mime: "@file/pdf"`), подпись в ответе —
в `document.file.data`.

В описании запроса приложение показывает организацию: `EGOV_ORG_NAME`, `EGOV_ORG_BIN` (БИН вашей компании).

### 4. Включить в админке (/admin → Флаги)

* `qualified_signature` — подписание документов ЭЦП (можно по компаниям);
* `eds.egov_mobile` — подписание в eGov mobile / eGov Business;
* `auth.eds_login` — вход по ЭЦП через NCALayer;
* `auth.egov_mobile` — вход через eGov mobile.

Если флаги включены, а `EDS_NCANODE_URL` не задан, `python -m app.cli preflight` покажет ошибку; в
production подпись без NCANode не принимается вовсе.

## Надёжность

* Таймаут обращения к NCANode — 30 секунд (OCSP/TSP под нагрузкой отвечают медленно); при серии сбоев
  срабатывает автоматический выключатель (circuit breaker), запросы не копятся.
* Если NCANode или eGov недоступны, работа не останавливается: остаётся подписание кодом из SMS (простая
  электронная подпись по договору), повторная проверка ЭЦП доступна позже.
* Каждое обращение пишется в журнал интеграций (без персональных данных).

## Проверка перед запуском

1. Вход через NCALayer ключом AUTH физлица, привязанного к аккаунту.
2. Подписание договора-заявки ключом подписи юрлица через NCALayer — на странице «Подписи» все проверки ✓.
3. То же через eGov Business по QR (после одобрения Smart Bridge).
4. Ключ чужой компании — отказ «owner»; просроченный или отозванный сертификат — отказ.
5. Повтор того же nonce, nonce из другого браузера — отказ.
6. Повторная проверка подписи на странице «Подписи» — проходит.

## Разработка

Без `EDS_NCANODE_URL` и не в production вместо NCALayer ключ создаётся в браузере (WebCrypto) и заверяется
тестовым УЦ, а под QR есть кнопка «Тестовый телефон», которая играет роль eGov mobile.
